# Visitas

Privacy-first web analytics for Cloudflare Workers: the tracker encrypts every visit **in the visitor's browser**, the Worker decrypts it just long enough to store it in D1, and a light/dark dashboard turns the data into charts, tables and fingerprint controls.

```
┌──────────────┐    RSA-OAEP + AES-256-GCM     ┌───────────────────┐
│  /tracker.js │ ───────────────────────────▶  │  Worker (vinext)  │
│  (generated) │    signed HMAC-SHA256         │  /api/track       │
└──────────────┘                               └─────────┬─────────┘
       ▲                                                 │
       │ blocklist + public key                          ▼
       │                                         ┌───────────────┐
       │                                         │  Cloudflare   │
       │                                         │  D1 database  │
       │                                         └───────┬───────┘
       │                                                 │
┌──────┴───────┐        session cookie (JWT)     ┌───────▼───────┐
│  Websites    │                                 │   Dashboard   │
│  with the    │                                 │  /  /blocked  │
│  tracker     │                                 │  /keys        │
└──────────────┘                                 └───────────────┘
```

## Features

- **Client-side encryption.** The tracker hybrid-encrypts the payload with a per-visit AES-256-GCM key, wrapped with the active RSA-2048 public key (RSA-OAEP + SHA-256). Plaintext never touches the network.
- **Dynamic, signed, obfuscated tracker.** `GET /tracker.js` is generated per request: it embeds the current public key, the current blocklist and an HMAC-SHA256 signature that `/api/track` verifies before accepting anything. The bundle is built by `scripts/build-tracker.mjs` (no comments, encoded strings, renamed identifiers, flattened control flow) so it cannot be read to infer what it does.
- **Fingerprint blocking.** The blocklist travels inside the tracker. A blocked browser is stopped (`window.stop()`) and gets an "Access blocked" screen before the page becomes visible; the API still counts the hit anonymously.
- **Self-managed key rotation.** The Worker generates the RSA key pair itself, stores it in D1 and rotates it automatically (default: every 30 days). Retired keys are kept for a grace period so in-flight trackers keep working, then deleted.
- **D1 storage.** A `visits` table with promoted columns for fast aggregations plus JSON columns for the full payload, a `blocked_fingerprints` table and a `tracker_keys` table for key rotation.
- **Dashboard.** Overview with timeline, browsers, OS, devices, countries, pages, referrers, network, WebGL renderers and more; visit feed with infinite-scroll pagination, expandable rows with the full decrypted payload and CSV export. Light theme by default, dark theme available from the sidebar.
- **Admin tooling.** Fingerprint blocklist management, key rotation page, login with credentials stored as Worker secrets.
- **Production ready.** Nonce-based CSP, hardened headers, rate limiting, observability enabled, custom domain ready.

## Getting started

### 1. Install dependencies

```bash
npm install
```

### 2. Create the D1 database

```bash
npx wrangler d1 create cf-visitas
```

Copy the returned `database_id` into `wrangler.jsonc` (replacing the placeholder).

### 3. Generate the Worker secrets

```bash
npm run keys:generate
```

The script prints a `.dev.vars` block for local development and the `wrangler secret put` commands for production:

| Secret                | Purpose                                             |
| --------------------- | --------------------------------------------------- |
| `ADMIN_USER`          | Dashboard username                                  |
| `ADMIN_PASSWORD`      | Dashboard password                                  |
| `SESSION_SECRET`      | HMAC key for session cookies (32+ bytes)            |
| `TRACKER_SIGNING_KEY` | HMAC key for tracker config signatures (32+ bytes)  |

> The tracker encryption key pair is **not** configured by hand: the Worker generates it on first use, stores it in D1 and rotates it automatically.

### 4. Apply the migrations

```bash
npm run db:migrate          # local development
npm run db:migrate:remote   # production
```

### 5. Run it

```bash
npm run dev       # vinext dev server
npm run preview   # production build + wrangler dev
```

Both commands run `npm run build:tracker` first, which obfuscates `tracker/tracker.source.js` into `tracker/tracker.dist.js` (gitignored).

### 6. Deploy

```bash
npm run deploy
```

The Worker is published with:

- the custom domain `visitas.manalejandro.com` (see `routes` in `wrangler.jsonc`),
- observability enabled (Workers Logs + traces),
- source maps uploaded for readable stack traces.

## Embedding the tracker

Add this snippet before `</head>` on every page you want to measure:

```html
<script src="https://visitas.manalejandro.com/tracker.js"></script>
```

The tracker:

1. Collects stable browser signals (user agent, screen, timezone, languages, canvas, WebGL, audio, fonts, hardware, connection…).
2. Computes a SHA-256 fingerprint.
3. Checks the signed blocklist — blocked browsers are stopped before rendering.
4. Hybrid-encrypts the payload and posts it to `/api/track` with the signed config.

It is render-blocking on purpose: it runs before the body is parsed so blocked browsers never see content. When the blocklist is empty there is no delay.

> **Local development:** Wrangler rewrites the request host to the configured custom-domain route, so `/tracker.js` would point at production. Set `TRACKER_ENDPOINT_ORIGIN` in `.dev.vars` to the port of the dev server you are using (`http://localhost:8787` for `npm run start`/`npm run preview`, `http://localhost:3001` for `npm run dev`).

## How the tracker is secured

| Layer               | Mechanism                                                                                       |
| ------------------- | ----------------------------------------------------------------------------------------------- |
| Payload encryption  | AES-256-GCM data key wrapped with RSA-2048 OAEP (SHA-256) — per visit                            |
| Request authenticity| HMAC-SHA256 signature over `v1.<kid>.<iat>.<exp>.<blocklistHash>`, verified by `/api/track`      |
| Key management      | Worker-generated RSA pair in D1, automatic rotation (`TRACKER_KEY_ROTATION_DAYS`, default 30)    |
| Key history         | Retired keys kept for 3 days for decryption, then deleted                                        |
| Blocklist           | Fingerprints are SHA-256 hashes; the blocklist is embedded in the signed tracker                 |
| Code protection     | Tracker obfuscated at build time: no comments, base64 string array, renamed identifiers, flattened control flow |
| Admin auth          | HttpOnly session cookie (JWT, HS256, 7 days) + timing-safe credential comparison + rate limiting |
| Transport           | HTTPS enforced by Cloudflare; nonce-based CSP; HSTS, nosniff, frame-ancestors 'none'             |

## API reference

| Method | Route                | Auth | Description                                  |
| ------ | -------------------- | ---- | -------------------------------------------- |
| GET    | `/tracker.js`        | –    | Generated tracker with config + blocklist     |
| POST   | `/api/track`         | sig  | Encrypted visit payload / blocked hit beacon  |
| POST   | `/api/login`         | –    | Sign in (sets session cookie)                 |
| DELETE | `/api/login`         | –    | Sign out                                      |
| GET    | `/api/visits`        | ✔    | Paginated visit feed (`range`, `limit`, `offset`) |
| GET    | `/api/blocked`       | ✔    | List blocked fingerprints                     |
| POST   | `/api/blocked`       | ✔    | Block a fingerprint (`fingerprint`, `reason`) |
| DELETE | `/api/blocked`       | ✔    | Unblock (`?fingerprint=…`)                    |
| GET    | `/api/export`        | ✔    | CSV export (`range`)                          |
| POST   | `/api/keys/rotate`   | ✔    | Rotate the tracker key immediately            |

## Key rotation

- A new RSA key pair is generated lazily: when the active key is missing or older than `TRACKER_KEY_ROTATION_DAYS`.
- Rotation is race-safe: concurrent isolates converge on a single active key.
- Retired keys stay available for decryption for `KEY_GRACE_DAYS` (3 days) and are then deleted.
- Admins can force a rotation from the **Keys** page; cached `tracker.js` responses pick it up within 5 minutes.
